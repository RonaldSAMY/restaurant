Containers, modules and the order lifecycle

Containers (Docker Compose)

flowchart LR
  B["Browser"] -->|"https://localhost"| PX["proxy (Caddy)"]
  PX -->|"/"| W["web (Next.js)"]
  PX -->|"/api/*"| A["api (NestJS)"]
  W -->|"server-side only"| A
  A --> PG[("postgres")]
  A --> R[("redis")]
  M["migrate (one-shot)"] --> PG
  SD["seed (one-shot)"] --> PG

The browser only ever talks to Caddy, so the whole app is one origin. Cookies just work, and CORS never comes up. (AD-15)

NestJS modules: who may import whom

flowchart LR
  realtime["realtime (gateway)"] --> auth
  realtime --> orders
  orders --> menu
  auth --> common
  orders --> common
  menu --> common

Imports only go one way, so there are no circular module imports. The Socket.IO server is reached through a small ref in common/. (AD-3)

Inside a rule-heavy module

flowchart TD
  C["Controller / Guard"] --> S["Service"]
  S --> D["Domain (pure TS)"]
  S --> P["Port (interface)"]
  X["Adapter: Prisma / Redis"] --> P

Rules like "RECEIVED can only become PREPARING" live in pure domain classes, so unit tests need no database. (AD-3, AD-7)

Shared contract package

flowchart LR
  web["apps/web"] --> shared["@restaurant/shared (Zod)"]
  api["apps/api"] --> shared
  shared --> zod["zod"]

Each request, response and socket event is defined once as a Zod schema. The api validates with it, and the web parses responses with it. (AD-2)
