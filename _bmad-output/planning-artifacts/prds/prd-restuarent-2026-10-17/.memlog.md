- (event) Create intent; initial scope from user: MVP public menu, guest ordering tracked by order reference, kitchen staff login moving orders Received->Preparing->Ready, 3 kitchen sections (a la carte cooked-to-order, fast food & drinks, takeout). Post-MVP: customer accounts w/ order history, promo coupons from order history.
- (decision) Stakes: study/demo project (hobby-level rigor, ~2-page PRD); goal is to exercise real features across the stack
- (decision) MVP timebox: 2 days, including authentication + authorization and tests
- (decision) Tech stack: NestJS, Next.js, Prisma+PostgreSQL, Redis (cache + token store), RabbitMQ; recorded in addendum (implementation, not PRD)
- (decision) Form factor: web app (customer-facing + kitchen staff)
- (decision) Working mode: Fast path (user answered batched gap questions)
- (decision) MVP auth: only kitchen staff log in; customers are guests
- (decision) MVP kitchen: single kitchen queue, no section split (a la carte / fast food & drinks deferred) - keep simple
- (decision) Takeout dropped from MVP
- (decision) No payment in MVP
- (decision) Customer sees status updates without manual reload; no Cancelled state in MVP
- (decision) RabbitMQ deferred post-MVP
- (decision) Redis in MVP: menu item cache + JWT session/refresh-token store; guest gets a session so a page refresh restores order tracking
- (assumption) Staff accounts and menu are seeded; no admin UI in MVP
- (assumption) Order reference is unguessable for tracking link; short display number for counter call-out (from research digest, OWASP IDOR)
- (decision) Order lifecycle extended: Received (waiting to be taken) -> Preparing (taken, in preparation) -> Ready (waiting for collection) -> Collected (done). Order chain completes at Collected; supersedes 'Ready is final'
- (decision) No past orders kept for MVP; Guest Session ends when the Order is Collected; returning guest starts fresh. Resolves open questions on Ready-order board retention and guest session lifetime
- (assumption) Kitchen Staff mark Collected at handover; Collected orders leave the Kitchen Board; one Guest Session tracks one Order
- (decision) Status names confirmed: Received / Preparing / Ready / Collected
- (decision) Uncollected Ready orders stay on the board until staff mark Collected; Guest Session expires after 24h
- (decision) One open Order per Guest Session: Guest cannot place another Order until the current one is Collected (simplicity); supersedes assumption 'another Order starts a new Guest Session'
- (decision) Finalize memlog audit: all entries captured; short counter display number set aside - staff call out Guest name instead (simplicity)
- (decision) Order read access: own Guest Session or Order Reference, until 24h after placement, then not-found; Guest Session never grants access to other Orders. Resolves review high finding (FR-3/FR-4/FR-7/6.2 conflict)
- (decision) All Orders retained permanently in the database (for future accounts/history); 24h limit governs access only
- (decision) Real-time push of Order Status changes to tracking page and Kitchen Board (user prefers WebSocket - addendum)
- (decision) Staff tokens: access token 5 min, refresh token 1 hour; logout revokes
- (decision) Menu cache refreshed when seed is re-run; user will add items via seed for testing
- (decision) Order Reference: 6-char random alphanumeric, typeable and non-sequential
- (decision) No-shows: uncollected Orders stay on board until staff mark Collected; no-show handling is a non-goal
- (assumption) Real-time target under 2 s; refresh token rotates on use so an active staff member stays logged in, idle >1h requires login
- (decision) Remaining assumptions (name-only guest, forward-only status, seeded staff + menu) accepted as MVP defaults at finalize; owner Ronald, revisit when accounts/admin land
- (decision) FR-7/FR-3 overlap on own-Order access kept intentionally: FR-3 defines the session scope, FR-7 anchors the authorization test
- (event) PRD finalized
