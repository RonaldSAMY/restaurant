## Intent

**Problem:** Guests cannot order yet. There is no `Order` storage and no placement endpoint, so the kitchen gets nothing and the Guest gets no Order Reference.

**Approach:** Add `Order`/`OrderItem` (Prisma + migration) and an `orders` module (domain `OrderReference`, `OrderRepository` port + Prisma adapter, `OrdersService.place`, controller). Add `POST /api/v1/orders` (`@Public()`). It takes the shared `PlaceOrderRequest`, copies names and prices from `MenuItem` and returns `201 GuestOrderView`. The Guest Session cookie and the 409 rule belong to Story 2.2.

## Boundaries & Constraints

**Always:**
- Shared Zod schemas `PlaceOrderRequestSchema` / `GuestOrderViewSchema` live in `packages/shared`. Types are `z.infer`. The route `orders` goes in `ApiRoutes`.
- Limits: `guestName` is trimmed, 1–60 chars. `items` has 1–50 lines. `quantity` is an int from 1 to 99. `menuItemId` is a UUID. Unknown keys (e.g. `priceCents`) are stripped by Zod and ignored.
- Duplicate `menuItemId` lines are merged into one line with the summed quantity, in the order of first appearance. A merged quantity > 99 → `400 VALIDATION_FAILED`. Merging happens in `OrdersService`, not in shared, because shared holds no business rules.
- Names and prices come from Postgres `MenuItem` through a new `MenuService.findItems(ids)`. `totalCents = Σ quantity × unitPriceCents`. Order and items are written in one Prisma call, so it is atomic.
- `placedAt` comes from the injected `Clock` port. The status is `RECEIVED`.
- `OrderReference` is pure TS with no framework imports. It returns 6 chars `[A-Z0-9]` from `node:crypto` without modulo bias. A `P2002` on insert retries with a new reference, up to 5 attempts, then rethrows.
- The response never contains the Order UUID. `placedAt` is an ISO-8601 UTC string. Log `Order placed` with `reference` only.
- The migration also adds `CHECK ("priceCents" >= 0)` on `MenuItem` (retro item 8), plus `quantity > 0`, `unitPriceCents >= 0` and `totalCents >= 0`.

**Never:** no `guest_session` cookie, no Redis, no 409 rule (that is Story 2.2). No lookup or current-order endpoints. No web changes. No `forwardRef`. No `MenuItem` join on Order reads. No new dependencies.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Happy path | valid name, 2 lines of seeded items | `201 GuestOrderView`, status `RECEIVED`, server total | N/A |
| Client price | line carries `priceCents: 1` | stored and returned price = `MenuItem.priceCents` | ignored |
| Empty basket | `items: []` | no Order | `400 VALIDATION_FAILED` |
| Bad quantity | `quantity: 0` or `1.5` | no Order | `400 VALIDATION_FAILED` |
| Empty name | `guestName: "  "` | no Order | `400 VALIDATION_FAILED` |
| Unknown item | random UUID `menuItemId` | `Order` count unchanged | `400 MENU_ITEM_NOT_FOUND` |
| Duplicate item | same `menuItemId` on 2 lines, qty 2 + 3 | one line, quantity 5 | N/A |
| Duplicate over cap | same `menuItemId`, qty 60 + 60 | no Order | `400 VALIDATION_FAILED` |
| Same name twice | two placements, same `guestName` | both 201, different references | N/A |
| Reference collision | first generated reference already taken | retried, 201 with a new reference | after 5 collisions → 500 `INTERNAL` |

## Design Notes

`OrderReference.generate` uses `crypto.randomInt(36)` per char, which is unbiased. Retry is caught only on `PrismaClientKnownRequestError` with `code === 'P2002'`. `id` is a random UUID, so the reference is the only realistic unique conflict.
